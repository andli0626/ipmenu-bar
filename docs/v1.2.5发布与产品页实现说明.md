## 二、发布链路总览

两条链路互相独立，靠“版本号”这一个点对齐：

```
① 版本发布
   改三处版本号 → commit → push main → 打 tag v1.2.5 → push tag
        └→ GitHub Actions: build(macOS universal / Windows x64) → release(汇总资产)
              └→ GitHub Release: dmg + setup.exe + msi

② 产品发布页
   docs/index.html + assets/ + downloads/ + .nojekyll → commit → push main
        └→ GitHub Pages（Deploy from a branch: main / docs）
              └→ https://andli0626.github.io/ipmenu-bar/
```

两条链路都只依赖 `main` 分支，但**触发条件不同**：Release 认 tag（`v*`），Pages 认 `docs/` 目录的内容变更。因此“发一个版本”实际上是两步：先发版本，再把页面的版本号、文件名、SHA 与下载链接更新后推一次。

## 三、版本发布实现

### 3.1 版本号为什么必须改三处

工作流在打包前做了强校验（`release.yml` 与 `build-check.yml` 各一份）：

1. `tauri.conf.json.version` 必须等于 `Cargo.toml` 的 `[package].version`；
2. tag 名去掉 `v` 后必须等于 `tauri.conf.json.version`。

只改一处会在构建阶段直接失败，或者出现“关于里显示旧版本、安装包文件名是新版本”的错位。本次三处同改：

```bash
# tauri.conf.json
"version": "1.2.5"

# src-tauri/Cargo.toml
[package]
version = "1.2.5"

# src-tauri/Cargo.lock（ipmenubar 自身的版本条目）
name = "ipmenubar"
version = "1.2.5"
```

`Cargo.lock` 容易被漏掉：它不参与上面的两项校验，但根包版本写在 lock 里。不改的话，构建时 Cargo 会自行改写它，造成“构建产物提交到工作区”的隐式变更；在启用 `--locked` 的流水线里则直接失败。三处一起改、一起提交，才能保证可复现。

### 3.2 提交与触发

```bash
git add -A
git commit -m "chore(release): 版本号同步至 v1.2.5"
git push origin main          # 先推主干，让 build-check 先跑一遍
git tag -a v1.2.5 -m "IPMenuBar v1.2.5"
git push origin v1.2.5        # 推 tag，触发 release.yml
```

先推主干再推 tag 的原因：主干推送会触发 `Build Check`（`--no-bundle` 的快速编译校验），几十秒到两三分钟就能知道版本号与编译有没有问题；如果先推 tag，失败时会在 Release 页留下一次失败记录。

### 3.3 工作流实际执行

`release.yml` 采用 **build → release** 两段式，任一平台失败都不会产生“只有一半资产”的 Release。

| Job | Runner | 命令 | 产物 |
|---|---|---|---|
| macOS (universal) | `macos-latest` | `tauri build --target universal-apple-darwin --bundles dmg` | 单个 dmg（arm64 + x64） |
| Windows (x64) | `windows-latest` | `tauri build --bundles nsis,msi` | setup.exe + msi |
| Publish release | `ubuntu-latest` | `gh release create/upload --clobber` | 汇总三个资产 |

产物会被统一改成 ASCII 文件名，避免中文 `productName`（`ip地址`）在下载 URL 里被 percent-encode：

```
IPMenuBar_${VER}_${asset_tag}.dmg / .msi / -setup.exe
```

本次结果：Release #5 `completed successfully`，Build Check #6 `completed successfully`。

## 四、产品发布页实现

### 4.1 参考对象与方案取舍

参考站点（`zchenmaker.github.io/Epoint-video-guide`）能在国内直连，不是因为网络通畅，而是因为它**排除了所有会失败的环节**：单个纯静态页、系统字体、同源样式、同源下载，不使用 `raw.githubusercontent.com`、`objects.githubusercontent.com`、`codeload.github.com` 等高风险子域，也不把 zip 挂在 Release 上。

本次照此落地，并结合“单文件交付”的要求做了两点强化：

- **样式与脚本全部内联**，整页只有 1 个 HTML 请求 + 3 张同源图片，比“HTML + 外链 CSS”更少一次往返；
- **安装包放入仓库 `docs/downloads/`**，页面用相对路径 `downloads/...` 引用，下载请求始终落在 `github.io` 这一个域名上。

代价是仓库体积增加约 15 MB，且安装包会在仓库与 Release 各存一份；这是“国内可下载”换来的确定性，后续发版需要同步替换（见第八节）。

### 4.2 目录结构

```

├── .nojekyll                  # 空文件，跳过 Jekyll 处理
```

沿用参考方案里的检查规则，对 `docs/` 全量扫描，检查项包括 Google Fonts、jsDelivr/unpkg/cdnjs、境外统计、`raw.githubusercontent` / `codeload.github` / `objects.githubusercontent`、`releases/download`、bootcdn / staticfile / polyfill.io。

结果：**未命中任何一条**。页面唯一的外链是页脚指向 `github.com` 的“源码仓库 / 更新日志”，它是用户主动点击的跳转，不参与页面渲染，不影响首屏可用性。

### 4.5 响应式与健壮性处理

实现过程中修掉的三类问题，值得记录：

1. **网格被内容撑宽**：`grid-template-columns: 1fr 1fr` 的列最小宽度默认是 `auto`，菜单栏模拟图与等宽地址会把列撑出视口，导致移动端文字被裁。改为 `minmax(0, 1fr)`，并给 `.stage` 加 `width:100%; min-width:0`。
2. **动画导致内容不可见**：滚动出现动画初始 `opacity:0`，一旦观察器未触发就是白屏。改为“默认可见，只有 JS 生效时才隐藏”（`html.js .reveal`），并加 1.4 s 兜底，将全部元素置为可见。
3. **无 JS 场景**：所有内容都在 HTML 里，不依赖 JS 渲染；导航使用原生锚点，折叠使用原生 `<details>`。

### 4.6 启用 GitHub Pages

仓库此前未开启 Pages（`andli0626.github.io/ipmenu-bar` 返回 404）。开启路径：

```
Settings → Pages → Build and deployment
  Source: Deploy from a branch
  Branch: main
  Folder: /docs
  → Save
```

保存后 GitHub 会立刻排队构建（首次通常 1–10 分钟）。本次约 1 分钟内生效，验证方式是直接请求站点根路径与两个关键资源（图标、dmg），均为 200。

> 注意：`docs/` 下的 Markdown 文档与截图也会随站点公开（免费账号要求仓库为 public）。若其中有内部信息，应移到站点目录之外，不要靠“页面没链接”来当保密手段。

## 五、本机环境问题与处置

本次发布在本机遇到四个问题，都不是代码问题，但每一个都能让发布卡住。

### 5.1 全局 `insteadOf` 把 GitHub 改写到失效代理

**现象**：`git clone` 报 `LibreSSL SSL_connect: SSL_ERROR_SYSCALL in connection to ghfast.top:443`。

**根因**：`~/.gitconfig` 有一条全局改写：

```ini
[url "https://ghfast.top/https://github.com/"]
    insteadOf = https://github.com/
```

所有 `https://github.com/` 地址都会被转发到 `ghfast.top`，而该代理当前主域 SSL 握手失败（实测 github.com 直连 200）。

**处置**：
- 读操作（clone / ls-remote）用 `GIT_CONFIG_GLOBAL=/dev/null` 绕过改写，直连官方源；
- 写操作（push）用一份“去掉了 `insteadOf`、保留 user 与 credential.helper”的临时配置（`/tmp/gitconfig-noRewrite`），配合 SSH 推送；
- **没有修改用户的全局配置**，只在单次命令内生效。

副作用：克隆时 `origin` 会被写成代理地址，需要手动 `git remote set-url origin https://github.com/andli0626/ipmenu-bar.git` 修正。

### 5.2 大体积 push 被中断

**现象**：推送含 15 MB 安装包的提交时报 `Connection closed by 198.18.0.26 port 443`，仓库未更新。

**根因**：本机 SSH 走 TUN 代理下的 `ssh.github.com:443`（`~/.ssh/config` 显式配置，因为 22 端口被封），链路在长上传中被打断。

**处置**：给 `GIT_SSH_COMMAND` 加 keepalive 后重推，成功：

```bash
GIT_SSH_COMMAND="ssh -o ServerAliveInterval=20 -o ServerAliveCountMax=6 -o IPQoS=throughput" \
  git push git@github.com:andli0626/ipmenu-bar.git main:main
```

判断标准是输出的 `8bbccc3..5e2112d  main -> main`，而不是退出码。

### 5.3 GitHub REST API 匿名限流

**现象**：用 `api.github.com` 轮询 Actions 状态，几分钟后返回 `403 rate limit exceeded`（60 次/小时，按 IP 计）。

**处置**：改用网页侧信息验证——`github.com/<repo>/actions` 看运行状态，`releases/tag/v1.2.5` 与 `releases/expanded_assets/v1.2.5` 看资产名、体积与 SHA。这类页面不消耗 API 配额，也足够做发布验收。

### 5.4 无头浏览器最小窗口宽度

**现象**：用 `--window-size=390` 截图，页面右侧文字被裁，误判为移动端横向溢出。

**根因**：Chrome 无头模式受系统窗口最小宽度限制，实际布局视口是 500 px，而截图画布只有 390 px，产生“看起来溢出”的假象。

**处置**：用注入脚本读取 `window.innerWidth / scrollWidth / 各元素 getBoundingClientRect()` 复核，确认 `scrollWidth < innerWidth`、无超宽元素；再以 500 px 重新截图验收。**不要只靠截图判断布局问题**。

## 七、完整复现步骤

以下命令按顺序执行即可复现一次“版本发布 + 页面更新”。假设本机已配置 SSH key 且 `git@github.com` 可认证。

```bash
# 0. 进入仓库
cd /path/to/ipmenu-bar

# 1. 同步版本号（三处）
#    src-tauri/tauri.conf.json / Cargo.toml / Cargo.lock

# 2. 更新发布页里的版本相关内容（见第八节清单）

# 3. 准备安装包：从本次 Release 下载，落到 docs/downloads/

grep -nEo 'fonts\.googleapis|fonts\.gstatic|cdn\.jsdelivr|unpkg\.com|cdnjs\.cloudflare|google-analytics|raw\.githubusercontent|codeload\.github|objects\.githubusercontent|releases/download' docs/index.html

# 5. 提交并推主干

# 6. 打 tag 触发多端打包

# 7. 验收
#    - Actions: Release 工作流 build 与 release 均绿
#    - Release 页: 三个资产齐全，sha256 与本地一致
#    - 站点: curl -I https://andli0626.github.io/ipmenu-bar/
```

5. 发版后等 1–10 分钟再验收，Pages 构建有延迟，可用 `?v=` 查询串强制刷新缓存。

## 九、经验与风险

**做对的地方**

- 用 tag 作为唯一发布开关，版本号与 tag 强校验，避免了“发出去的包版本错位”这类不可追溯问题；
- 产物统一 ASCII 命名，下载链接稳定，脚本与下载器都不会被中文编码坑到；
- 页面“自包含 + 同源下载”，把可用性建立在自身设计上，而不是赌网络状况；
- 发布页把 SHA256 放在页面上并可一键复制，安装包可自校验，弥补了未签名的信任缺口。

**需要接受的限制**
